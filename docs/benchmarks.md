# 벤치마크와 실전 과제

로컬 모델로 opencode 코딩 에이전트를 돌릴 때 무엇이 빠르고, 무엇이 끝까지 돌아가는 결과물을 내는지 잰 기록.

> **읽기 전에**
> - 실전 과제는 **모델당 1회(n=1)** 다. 같은 모델도 다시 돌리면 달라질 수 있으므로 경향으로만 읽고 단정하지 않는다.
> - 게임 품질 판정은 **사람이 결과물을 직접 플레이해 본 판정**이다(자동 채점이 아님).
> - 속도·시간 수치는 서버 로그(`llm-server.log`)에서 집계했다. 모든 측정은 GPU 에서 한 번에 한 모델로 했고, 실전 과제는 `opencode --auto -m halo/<모델>` 새 세션이다.
> - 서버·모델 사양은 [hardware.md](hardware.md), [models.md](models.md).

## 1. 표준 시험 (2026-10-17)

같은 하네스로 router 에 올라 있던 모델 14종을 한 번에 하나씩, GPU 에서 돌린 값이다. `mcv` 는 아직 재지 않아 없다.
표의 값은 **llama.cpp b11701**(현재 서버 엔진)에서 잰 것이다. 앞서 b11539 에서 한 번 잰 값은 [엔진 비교](#엔진-비교-b11539-대-b11701)에 있다.

**방법**
1. 모델에게 JS 함수 `rotateMatrix`(행렬 90도 회전)와 `clearLines`(테트리스 줄 삭제)를 쓰게 하고, `node` 로 정해 둔 정답과 대조해 자동 채점한다(최대 4000 토큰).
2. 이어서 약 1만 토큰짜리 긴 프롬프트를 보내 프롬프트 읽기 속도를 잰다(토큰 수는 모델 토크나이저마다 9.5천~1.2만).
3. 「교체 포함 첫 응답」은 첫 요청을 보내 답이 끝날 때까지의 벽시계 시간이다. router 가 직전 모델을 내리고 이 모델을 올리는 시간 **과** 답을 생성하는 시간(생각하는 모델은 생각하는 시간까지)이 함께 들어 있다. 앞 모델이 무엇이었는지에 따라 교체 비용이 달라진다.
4. 채점은 확률적이다. 같은 모델도 다시 돌리면 답이 달라진다(`q36` 과 `c7r` 은 b11539 에서 통과했지만 b11701 재측정에서 clearLines 가 틀렸다). 그래서 한 번의 통과/실패 표시 대신 **통과 횟수**(두 함수가 모두 맞은 실행 수 / 전체 실행 수)로 적는다. 실행 수는 대부분 2회(b11539 1회 + b11701 1회), `mel` 3회, `bolt` 2회(b11701 에서 생각 켬 1회 + 끔 1회), `lfm` 1회다.

읽을 때 주의:
- 생성 속도는 대체로 세 무리다: 75~91 t/s (`q36` `orn` `lfm`), 54~69 t/s (`c1` `cn` `aw` `bolt`), 23~29 t/s (`c7` `c7r` `mg` `q38` `ff` `fn`). 예외가 `mel`(17.9 t/s)인데, 이것은 b11701 에서만 이렇게 느리다(아래 비교). 모델 크기 하나로는 속도가 설명되지 않는다 - 추측 디코딩 유무, dense/MoE, 텐서 일부를 CPU 쪽에 두는지가 함께 작용한다. 같은 3B 활성이라도 추측 디코딩이 없는 `cn`(55.8)은 MTP 가 있는 `q36`·`orn`(81~91)보다 느렸다 - 모델 크기 차이와 겹쳐 있어 원인을 따로 가르지는 않았다.
- 추측 디코딩이 없는 dense 모델은 (파일 크기 x 생성 속도)가 거의 일정하다: `c7` 8.1GB x 28.9 t/s = 약 234GB/s, `c1` 3.1GB x 68.6 t/s = 약 212GB/s. 토큰마다 가중치 전체를 한 번 읽는다고 단순 계산하면 이 서버가 200GB/s 안팎으로 읽는 셈이다 - 속도를 메모리 대역폭이 정한다는 설명과 맞는다([hardware.md](hardware.md#3-속도를-정하는-것)).
- 「긴 프롬프트 읽기」는 에이전트 체감에 크다 - 에이전트는 매 단계 문맥 전체를 다시 읽기 때문이다. 읽기는 `c1`(3057), `lfm`(1834)이 압도적으로 빠르고, `bolt`(415)·`fn`(357)·`mg`(331)·`ff`(315)·`q38`(301)이 느렸다. `mel` 의 524 는 b11701 에서 느려진 값이다.
- 통과 횟수는 표본이 2~3회뿐이라 순위로 쓰지 않는다. 다만 `fn`(0/2)과 `c1`(0/2)은 두 번 다 같은 모양으로 실패했고, 같은 계열 전체판 `ff`(2/2)나 7B `c7`(2/2)은 두 번 다 통과했다.
- 첫 응답은 8.8초(`c1`)에서 98.8초(`ff`)까지 모델마다 다르다. 생각이 긴 모델과 큰 모델이 길다(`ff` 98.8초, `mel` 87.9초, `mg` 65.5초, `lfm` 65.4초, `aw` 63.9초). `c7r` 의 9.4초는 직전에 `c7` 이 같은 파일을 읽어 파일 캐시가 남아 있었기 때문이다.
- 이 표는 코드 두 함수를 쓰는 짧은 시험이다. **끝까지 만든 결과물의 품질은 아래 실전 과제에서 갈렸고, 이 표의 순서와 다르다.**

### 작업 중 실측 (과거 값)

표준 시험 이전에 실전 과제를 돌리며 로그에서 집계한 값. 서브에이전트가 동시에 돌면 슬롯 4개가 속도를 나눠 쓰므로 표준 시험보다 낮게 나온다.

| | 생성 t/s | 읽기 t/s | GTT | 초안 수락률 |
|---|---|---|---|---|
| `cn` | 45~49 | 550~750 | 47.5G | - |

| `orn` | 94 (짧은 시험) / 실전 평균 49 | 600~630 | 29.8G | MTP 87% (단독) / 실전 66% |

- 서브에이전트가 동시에 돌 때 `mg` 는 갤러그에서 평균 7.2 t/s 까지 떨어졌다(dense 라 가장 크게 손해).
- 코드를 길게 쓰는 단계에서는 초안 수락률이 떨어져 가속 이득이 준다(MTP 50%대, DFlash 30%대). 생각을 켜면 MTP 수락률도 60%대로 내려간다.

## 2. 함수 단위 벤치 (2026-10-11)

테트리스 함수 3문제 x 2회(`node` 테스트로 자동 채점) + 벽돌깨기 HTML 한 파일(출력 한도 20000 토큰). GPU, 한 번에 한 모델.
시험을 믿기 전에 **정답 풀이로 하네스를 먼저 돌려** 기대값이 틀린 문제 2건을 잡았다.

| | 테트리스 6문제 | 벽돌깨기 |
|---|---|---|
| `q36` 생각 끔 | **6/6, 문제당 2~4초** | 1.4분 · 700줄 |
| `cn` | 6/6, 4~9초 | 1.4분 · 468줄, 요구 위반 4건 |
| `mg` low / high | 6/6 16~26초 / 6/6 34~124초 | 1.2분 · 206줄 / 3.8분 · 231줄 |

- **함수 벤치로는 모델 간 차이가 거의 보이지 않았다**(전부 6/6). 차이는 아래 실전에서 드러났다.
- 한 번에 내놓은 결과는 검수가 필요하다. `cn` 의 벽돌깨기 위반 4건: 오버레이가 클릭을 가로채 시작 불가 · 윗줄 점수가 반대 · 창을 줄이면 마우스 비율 미보정 · 일시정지 클릭 불가. `mg` low 도 오버레이가 클릭을 가로챘다.
- 받아 보고 제외한 모델(Qwen3.8 계열 등)의 결과는 [models.md](models.md#받아-봤지만-쓰지-않는-모델--검토-후-제외).

## 6. 알게 된 점

1. **함수 벤치 동률은 실전 동률이 아니다.** 끝까지 만든 결과물을 사람이 돌려 봐야 차이가 보인다.
2. **QA 서브에이전트를 둬도 조작 불가·진행 불가를 못 잡는다.** 화면을 보지 않는 테스트의 한계다(`cn` 테트리스, `orn` 갤러그).
3. **한 번에 긴 코드를 쓰는 모델보다 작게 나눠 쓰는 모델(`mg`)이 돌아가는 결과물을 냈다.**
4. **상대 경로 지시는 모델마다 다르게 풀린다.** 프롬프트에는 절대 경로를 쓴다(`q36` 이 폴더를 엉뚱한 곳에 만들었다).
5. **원작 재현 + 팀 페르소나 같은 큰 과제는 로컬 모델이 한 번에 끝내기 어렵다.** 다음 비교는 「버그를 알려 주고 고치게 하는 회차」가 낫다.
6. **서브에이전트는 부른 쪽 모델을 물려받는다**(에이전트에 model 지정이 없으면). 그래서 동시 서브에이전트는 슬롯을 나눠 쓴다.
7. 속도는 **메모리 대역폭**이 정한다 - 활성 파라미터가 작은 MoE 가 빠르고 dense 30B 는 느리다. 에이전트는 **읽기 속도**도 체감에 크다.
8. **추측 디코딩(MTP/DFlash)을 켜는 것만으로 판도가 바뀐다.** 초기 시험에서 MTP 를 끈 채 쟀던 값이 잘못된 결론의 원인이었다.

## 7. 남은 시험

- `mg` 결과물을 바탕으로 고치기 회차(원작풍 도트, 스테이지 난이도, 트랙터 빔).
- 나머지 모델에 증상을 알려 주고 고치게 하기(누가 빨리·정확히 고치나).
- 모델이 기록한 작업 시각 파일 vs 서버 로그 대조.
- `mel` `bolt` `lfm` 실전 과제, `mcv` 표준 시험과 실전, 필요하면 `ff` `q38` `c7` 계열의 실전 과제.
- `mel` 이 b11701 에서 느려진 원인 조사(엔진 변경 때문인지, 이 모델 구조와 엔진의 상호작용인지).
- 표준 시험을 모델당 3회 이상 돌려 통과율을 더 믿을 만하게 만들기(지금은 2회 안팎).
- `mg` low/xhigh 차이를 같은 과제로 따로 재기.
