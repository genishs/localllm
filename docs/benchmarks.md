# 벤치마크와 실전 과제

로컬 모델로 opencode 코딩 에이전트를 돌릴 때 무엇이 빠르고, 무엇이 끝까지 돌아가는 결과물을 내는지 잰 기록.

> **읽기 전에**
> - 실전 과제는 **모델당 1회(n=1)** 다. 같은 모델도 다시 돌리면 달라질 수 있으므로 경향으로만 읽고 단정하지 않는다.
> - 게임 품질 판정은 **사람이 결과물을 직접 플레이해 본 판정**이다(자동 채점이 아님).
> - 속도·시간 수치는 서버 로그(`llm-server.log`)에서 집계했다. 모든 측정은 GPU 에서 한 번에 한 모델로 했고, 실전 과제는 `opencode --auto -m halo/<모델>` 새 세션이다.
> - 서버·모델 사양은 [hardware.md](hardware.md), [models.md](models.md).

## 1. 표준 시험 (2026-10-17)

같은 하네스로 router 에 올라 있던 모델 13종을 한 번에 하나씩, GPU 에서 돌린 값이다. `lfm` `mcv` 는 추가 중이라 아직 없다.

> **엔진 빌드가 섞여 있다.** `bolt` 행만 llama.cpp **b11701** 에서 잰 값이고(그때는 생각이 켜져 있었다), 나머지 12종은 **b11539** 에서 잰 값이다. `bolt`·`mcv` 가 b11701 이상을 요구해 서버 엔진을 올렸고, 지금 전체를 b11701 에서 다시 재는 중이다 - 끝나면 이 표를 바꾼다.

**방법**
1. 모델에게 JS 함수 `rotateMatrix`(행렬 90도 회전)와 `clearLines`(테트리스 줄 삭제)를 쓰게 하고, `node` 로 정해 둔 정답과 대조해 자동 채점한다.
2. 이어서 약 9.8천 토큰짜리 긴 프롬프트를 보내 프롬프트 읽기 속도를 잰다.
3. 「교체 포함 첫 응답」은 router 가 직전 모델을 내리고 이 모델을 올리는 시간까지 포함한 첫 응답까지의 시간이다.

읽을 때 주의:
- 생성 속도는 대체로 네 무리다: 85~90 t/s (`q36` `orn` `mel`), 55~69 t/s (`c1` `aw` `cn`), 46 t/s (`bolt`, 생각을 켠 상태), 23~29 t/s (`c7` `c7r` `mg` `q38` `ff` `fn`). 모델 크기 하나로는 설명되지 않는다 - 추측 디코딩 유무, dense/MoE, 텐서 일부를 CPU 쪽에 두는지가 함께 작용한다. 같은 3B 활성이라도 추측 디코딩이 없는 `cn`(55.4)은 MTP 가 있는 `q36`·`orn`(87~90)보다 느렸다 - 모델 크기 차이와 겹쳐 있어 원인을 따로 가르지는 않았다.
- 추측 디코딩이 없는 dense 모델은 (파일 크기 x 생성 속도)가 거의 일정하다: `c7` 8.1GB x 29.0 t/s = 약 235GB/s, `c1` 3.1GB x 68.5 t/s = 약 212GB/s. 토큰마다 가중치 전체를 한 번 읽는다고 단순 계산하면 이 서버가 200GB/s 안팎으로 읽는 셈이다 - 속도를 메모리 대역폭이 정한다는 설명과 맞는다([hardware.md](hardware.md#3-속도를-정하는-것)).
- 「긴 프롬프트 읽기」는 에이전트 체감에 크다 - 에이전트는 매 단계 문맥 전체를 다시 읽기 때문이다. 읽기는 `c1`(3045), `mel`(2008)이 압도적으로 빠르고 `bolt`(417), 가지치기판 `fn`(356)·dense 30B `mg`(331)·전체판 `ff`(318)·dense 27B `q38`(300)이 느렸다.
- 채점을 통과하지 못한 것은 `fn`(rotateMatrix)과 `c1`(clearLines) 둘이다. 같은 Flash-Next 계열인데 `ff` 는 통과했다. 1.5B 가 실패하고 7B 가 통과했지만 이 시험은 두 함수뿐이고 모델당 1회라 원인이나 순위를 단정하지 않는다.
- `bolt` 의 103.5초는 추론을 약 1.25만 자 쓰는 시간이 포함된 값이다. 생각을 끈 간이 확인(같은 하네스의 정식 측정은 아님)은 생성 62.4 t/s, 작은 함수 하나가 1.2초였다.
- 첫 응답(교체 포함)은 6.4초(`c1`)에서 95.2초(`ff`), 103.5초(`bolt`)까지 모델마다 다르다. 교체 시간과 첫 토큰 생성 시간을 나눠 재지는 않았다. `c7r` 의 8.4초는 직전에 `c7` 이 같은 파일을 읽어 파일 캐시가 남아 있었기 때문이다.
- 이 표는 코드 두 함수를 쓰는 짧은 시험이다. **끝까지 만든 결과물의 품질은 아래 실전 과제에서 갈렸고, 이 표의 순서와 다르다.**

### 작업 중 실측 (과거 값)

표준 시험 이전에 실전 과제를 돌리며 로그에서 집계한 값. 서브에이전트가 동시에 돌면 슬롯 4개가 속도를 나눠 쓰므로 표준 시험보다 낮게 나온다.

| | 생성 t/s | 읽기 t/s | GTT | 초안 수락률 |
|---|---|---|---|---|
| `cn` | 45~49 | 550~750 | 47.5G | - |
| `q36` | 71~86 | 680~900 | 30.8G | MTP 81~94% |
| `orn` | 94 (짧은 시험) / 실전 평균 49 | 600~630 | 29.8G | MTP 87% (단독) / 실전 66% |
| `mg` | 20~30 | 190~310 | 22.4G | DFlash 75% (벤치) / 실전 27~44% |

- 서브에이전트가 동시에 돌 때 `mg` 는 갤러그에서 평균 7.2 t/s 까지 떨어졌다(dense 라 가장 크게 손해).
- 코드를 길게 쓰는 단계에서는 초안 수락률이 떨어져 가속 이득이 준다(MTP 50%대, DFlash 30%대). 생각을 켜면 MTP 수락률도 60%대로 내려간다.

## 2. 함수 단위 벤치 (2026-10-11)

테트리스 함수 3문제 x 2회(`node` 테스트로 자동 채점) + 벽돌깨기 HTML 한 파일(출력 한도 20000 토큰). GPU, 한 번에 한 모델.
시험을 믿기 전에 **정답 풀이로 하네스를 먼저 돌려** 기대값이 틀린 문제 2건을 잡았다.

| | 테트리스 6문제 | 벽돌깨기 |
|---|---|---|
| `q36` 생각 끔 | **6/6, 문제당 2~4초** | 1.4분 · 700줄 |
| `cn` | 6/6, 4~9초 | 1.4분 · 468줄, 요구 위반 4건 |
| `mg` low / high | 6/6 16~26초 / 6/6 34~124초 | 1.2분 · 206줄 / 3.8분 · 231줄 |

- **함수 벤치로는 모델 간 차이가 거의 보이지 않았다**(전부 6/6). 차이는 아래 실전에서 드러났다.
- 한 번에 내놓은 결과는 검수가 필요하다. `cn` 의 벽돌깨기 위반 4건: 오버레이가 클릭을 가로채 시작 불가 · 윗줄 점수가 반대 · 창을 줄이면 마우스 비율 미보정 · 일시정지 클릭 불가. `mg` low 도 오버레이가 클릭을 가로챘다.
- 받아 보고 제외한 모델(Qwen3.8 계열 등)의 결과는 [models.md](models.md#받아-봤지만-쓰지-않는-모델--검토-후-제외).

- 이 회차의 첫 `q36` 시도는 `--auto` 로 재시작하면서 모델이 기본값(`cn`)으로 바뀌어 섞였고, 서버 로그의 모델 교체 기록으로 발견해 비교에서 뺐다 -> [troubleshooting.md](troubleshooting.md#opencode-시작-모델의-우선순위).

## 5. 종합 순위와 쓰임새 (n=1)

| 기준 | 순위 |
|---|---|
| **완성도 (돌아가는 결과물)** | `mg` > `q36` > `cn` > `orn` (테트리스·갤러그 둘 다 `mg` 1위) |
| 속도 (작업시간) | `cn` > `q36` > `mg` ≈ `orn` (갤러그) |
| 원작다운 겉모습 | `q36`·`orn` > `mg` |

| 모델 | 쓰임새 |
|---|---|
| `mg` (Glimmer) | 시간이 걸려도 **돌아가는 결과물**이 필요할 때. 코드를 작게 나눠 쓰고 고치기를 반복한다 |
| `q36` | 기본 일꾼. 빠르고 테트리스 5/5. 갤러그 같은 큰 과제에서는 멈춤 버그 |
| `cn` | 가장 빨리 끝나는 초안. 짧게 끝내며 핵심 규칙을 틀리거나 지시(페르소나)를 건너뛴다. 짚어 주면 정확히 고친다 |
| `orn` | 벤치 점수와 팀 작업 성실도는 높지만 이번 실전에서는 조작 불가 버그. 표본 1회라 판단 보류 |
| `mel` | 표준 시험만 했고 실전 미실시. 읽기가 빠르고 가볍다 |
| `bolt` | 표준 시험만 했고(b11701) 실전 미실시. 도구 호출·터미널용으로 학습된 2비트 모델. 생각 켬/끔을 variant 로 고른다 |
| `fn` | 표준 시험 실패 (실험용) |
| `ff` `q38` `aw` `c7` `c7r` `c1` | 비교·기준선용: 표준 시험 값만 있다(`c1` 은 채점 실패, `aw` 는 세계 모델이라 에이전트 비교 대상이 아님) |
| `lfm` `mcv` | 추가 중 — 실측 전 |

## 6. 알게 된 점

1. **함수 벤치 동률은 실전 동률이 아니다.** 끝까지 만든 결과물을 사람이 돌려 봐야 차이가 보인다.
2. **QA 서브에이전트를 둬도 조작 불가·진행 불가를 못 잡는다.** 화면을 보지 않는 테스트의 한계다(`cn` 테트리스, `orn` 갤러그).
3. **한 번에 긴 코드를 쓰는 모델보다 작게 나눠 쓰는 모델(`mg`)이 돌아가는 결과물을 냈다.**
4. **상대 경로 지시는 모델마다 다르게 풀린다.** 프롬프트에는 절대 경로를 쓴다(`q36` 이 폴더를 엉뚱한 곳에 만들었다).
5. **원작 재현 + 팀 페르소나 같은 큰 과제는 로컬 모델이 한 번에 끝내기 어렵다.** 다음 비교는 「버그를 알려 주고 고치게 하는 회차」가 낫다.
6. **서브에이전트는 부른 쪽 모델을 물려받는다**(에이전트에 model 지정이 없으면). 그래서 동시 서브에이전트는 슬롯을 나눠 쓴다.
7. 속도는 **메모리 대역폭**이 정한다 - 활성 파라미터가 작은 MoE 가 빠르고 dense 30B 는 느리다. 에이전트는 **읽기 속도**도 체감에 크다.
8. **추측 디코딩(MTP/DFlash)을 켜는 것만으로 판도가 바뀐다.** 초기 시험에서 MTP 를 끈 채 쟀던 값이 잘못된 결론의 원인이었다.

## 7. 남은 시험

- `mg` 결과물을 바탕으로 고치기 회차(원작풍 도트, 스테이지 난이도, 트랙터 빔).
- 나머지 모델에 증상을 알려 주고 고치게 하기(누가 빨리·정확히 고치나).
- 모델이 기록한 작업 시각 파일 vs 서버 로그 대조.
- `mel` `bolt` 실전 과제, `lfm` `mcv` 표준 시험과 실전, 필요하면 `ff` `q38` `c7` 계열의 실전 과제.
- 엔진 b11701 에서 전 모델 표준 시험 재측정(진행 중) - 끝나면 1절 표와 `models.md`·README 의 수치를 바꾼다.
- `mg` low/xhigh 차이를 같은 과제로 따로 재기.
