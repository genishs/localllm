# 서버 하드웨어와 구성 기준

지금 쓰는 서버의 실제 사양과, 비슷한 서버를 만들 때 참고할 기준. 아래 사양은 현재 서버에서 확인한 값이다.
운영 방법은 [server.md](server.md), 모델은 [models.md](models.md).

## 1. 현재 서버

| 항목 | 내용 |
|---|---|
| 기종 | ASUS TUF Gaming A14 (FA401EA) 노트북 |
| CPU | AMD Ryzen AI MAX+ 392 - 12코어 / 24스레드 |
| GPU | 내장 Radeon 8060S (RDNA 3.5, gfx1151, 코드명 「Strix Halo」) |
| 메모리 | 64GB LPDDR5X **통합 메모리** (OS 인식 60.94GiB, 약 3GiB 는 펌웨어가 선점) |
| 전용 VRAM | 0.5GiB (카브아웃 - 전용 VRAM 은 이게 전부) |
| GPU 공유 메모리(GTT) | **56GiB** (커널 파라미터 `ttm.pages_limit=14680064`) |
| 저장장치 | NVMe 2TB (Fanxiang S770, 모델 파일) + NVMe 1TB (Samsung, OS). 모델 파일 총 약 300GB |
| OS | Ubuntu 26.04.1 LTS, 커널 7.0.0-38-generic |
| 그래픽 스택 | Mesa 26.0.8 (RADV Vulkan), libvulkan 1.4.341 |
| 실행기 | llama.cpp b11701 (`version: 0.7.0-dev`, commit 01fc3aae8, 2026-10-16) 공식 사전빌드, **Vulkan** 백엔드 |

통합 메모리라서 모델은 전용 VRAM(0.5GiB)이 아니라 **GTT**(GPU 가 쓰는 공유 구간)에 올라간다. 「VRAM 을 안 쓴다」는 것은 정상이다 - 확인은 GTT 로 한다.

## 2. 메모리 예산 (GiB)

```
설치            64.00     물리 DIMM
OS 인식         60.94     약 3.06 을 펌웨어가 부팅 전에 가져간다 (회수 불가)
 ├ GTT          56.00     고정(pinned) - 스왑으로 받칠 수 없다
 ├ VRAM 카브아웃  0.50     고정
 └ OS · 사용자    4.44     여기만 스왑이 받쳐 준다
```

- **GTT 를 더 올리면 OS 몫이 그만큼 줄어든다**: 58GiB 로 올리면 OS 에 2.44GiB, 60GiB 로 올리면 0.44GiB 가 남아 쓸 수 없다. 56GiB 는 이미 공격적인 값이다(OS 인식 메모리의 약 92%).
- GTT 페이지는 GPU 가 직접 접근하도록 커널이 **고정**해 둔 것이라 스왑 아웃이 되지 않는다. 메모리가 모자랄 때 스왑을 늘려도 GTT 는 해결되지 않는다.
- GTT 가 거의 가득 차면(실측 99.8%) 오류도 OOM 도 없이 처리가 사실상 멈추고 유닛은 살아 있는 채 로그만 갱신되지 않는 현상을 학습 작업에서 겪었다. 서빙에서 같은 증상을 확인한 것은 아니지만, 모델이 GTT 에 빠듯하게 들어가는 구성(`cn` 이 가장 가깝다)은 여유를 두고 쓴다.
- 설정 방법: `/etc/default/grub` 의 `GRUB_CMDLINE_LINUX_DEFAULT` 에 `ttm.pages_limit=14680064` 를 추가하고 `sudo update-grub` 후 재부팅한다. 값은 페이지 수다: 14,680,064 x 4KiB = 56GiB.
  - 확인: `cat /proc/cmdline`, `cat /sys/class/drm/card*/device/mem_info_gtt_total`(바이트). `/sys/module/ttm/parameters/pages_limit` 는 읽기 전용이라 재부팅해야 바뀐다. 이 커널에는 `amdgpu.gttsize` 가 없다.

## 3. 속도를 정하는 것

- **메모리 대역폭**이 생성 속도를 정한다. 그래서 활성 파라미터가 작은 MoE 는 빠르고(MTP 를 쓰는 `q36`·`orn` 은 표준 시험 81~91 t/s, 활성 2B 인 `lfm` 은 75 t/s) dense 30B 는 느리다(`mg` 26 t/s). 예외로 `mel` 은 b11701 에서만 17.9 t/s 로 느리다(조사 중 - [benchmarks.md](benchmarks.md#엔진-비교-b11539-대-b11701)).
- 확인용 계산: 추측 디코딩이 없는 dense 모델은 토큰마다 가중치 전체를 한 번 읽으므로 (파일 크기 x 생성 속도)가 일정해야 한다. 실제로 `c7`(8.1GB x 28.9 t/s)은 약 234GB/s, `c1`(3.1GB x 68.6 t/s)은 약 212GB/s 로 비슷하다 - 이 서버가 200GB/s 안팎으로 읽는다는 뜻이다(단순 계산이며 이론 최대치를 따로 재지는 않았다).
- 에이전트는 매 단계 문맥 전체를 다시 읽으므로 **프롬프트 읽기 속도**도 체감에 크다(표준 시험 301~3057 t/s).
- 추측 디코딩(MTP/DFlash)을 켜는 것만으로 속도가 크게 달라진다. 켜지 않은 채 잰 값으로 모델을 평가하면 틀린다.
- 수치는 [benchmarks.md](benchmarks.md).

## 4. 필요한 OS 설정

| 설정 | 이유 | 방법 |
|---|---|---|
| 서비스 사용자를 `render`, `video` 그룹에 | 그렇지 않으면 GPU 를 **데스크톱에 로그인해 있는 동안에만** 쓸 수 있다. 재부팅 후 아무도 로그인하지 않으면 경고 없이 CPU 로 돌아 10배 이상 느려진다 | `sudo usermod -aG render,video <사용자>` -> 재로그인/재부팅. 즉시 적용: `sudo setfacl -m u:<사용자>:rw /dev/dri/renderD128 /dev/dri/card1` (카드 번호는 `ls /dev/dri` 로 확인) ([상세](troubleshooting.md#재부팅-후-gpu-를-못-쓰고-cpu-로-돈다)) |
| `ttm.pages_limit` 커널 파라미터 | 모델이 올라갈 GTT 를 56GiB 로 | 위 2절 |
| 덮개를 닫아도 절전 안 함 (노트북) | 기본값은 전원이 꽂혀 있어도 덮개를 닫으면 절전 -> 서버와 LAN 접속이 끊긴다 | `server/lid-ac-ignore.sh` ([server.md](server.md#덮개를-닫아도-계속-돌게-노트북-서버)) |
| 방화벽에서 8080 을 클라이언트 IP 마다 허용 | ufw 가 켜져 있으면 PC 가 접속하지 못한다 | `server/llm-allow.sh <PC IP>` ([server.md](server.md#방화벽)) |
| llama.cpp 빌드는 ext4 에 | NTFS 에 두면 `.so` 심볼릭 링크가 깨져 서버가 뜨지 않는다 | [troubleshooting.md](troubleshooting.md#ntfs-에-둔-빌드가-안-뜬다) |

모델을 올렸을 때 `GTT` 사용량(표준 시험 값. 가중치 + KV 캐시 + 버퍼의 합이라 파일 크기와 똑같지는 않다).

| 별칭 | GTT | 파일 | 비고 |
|---|---|---|---|
| `cn` | 약 47.5G | 48.7GB | 가장 크다 - GTT 56GiB 의 85% |
| `q36` | 약 30.7~30.8G | 30.0GB | |
| `orn` | 약 29.8~30.0G | 29.2GB | |
| `mg` | 약 22.4~22.7G | 19.7GB + 초안 1.6GB | |
| `fn` | 약 30.2G | 58.4GB | 28.8GB 텐서 하나는 GPU 에 올리지 않고 mmap 으로 디스크에서 필요한 줄만 읽는다(`ff` 와 같은 방식) |
| `mel` | 약 13.4G | 12.9GB | 엔진을 b11701 로 올려도 GTT 는 그대로(13.3G -> 13.4G)인데 속도만 느려졌다 |
| `q38` | 약 27.7G | 22.0GB | dense 27B |
| `aw` | 약 28.9G | 29.3GB | 세계 모델 |

| `bolt` | 약 28.8G | 22.0GB (+mmproj 1.7GB, 초안 1.0GB) | llama.cpp b11701 에서 측정(생각 끔·켬 모두 28.8G) |
| `lfm` | 약 25.4G | 25.5GB | 활성 2B 하이브리드 MoE |

## 6. 규모 가이드 (보증 아님)

실제로 확인한 것은 이 서버(64GB 통합 메모리) 하나뿐이다. 아래는 그 경험에서 나온 가이드이며 보증이 아니다.

- **64GB 통합 메모리급**(Strix Halo 또는 비슷한 장비): 이 문서의 모델을 **한 번에 하나씩** 모두 돌릴 수 있었다.
- **32GB급 GPU 메모리**: 파일이 20~30GB 인 모델(`mg` `q36` `orn` `lfm` `q38` `aw` `bolt` 등)은 가능성이 있다. 문맥(KV)과 여유를 감안해 직접 시험해야 한다.
- 48GB 급 `cn` 은 GPU 가 주소 지정할 수 있는 메모리가 56GiB 급 이상 필요한 것으로 본다(이 서버에서는 56GiB 로 돌렸다).
- 75.8GB 인 `ff` 는 큰 텐서(28.8GB) 하나를 mmap 으로 디스크에서 읽어 GPU 점유를 46.5G 로 줄였지만, 그 대신 RAM·디스크 읽기에 기댄다(남은 RAM 최저 11.6G). 64GB 장비의 한계에 가깝다.
- 문맥이 32K 인 작은 모델(`c7` `c7r` `c1`)은 GTT 5~10GB 로 충분하다.
- **엔진 버전도 구성의 일부다.** 새 구조의 모델(`bolt`, `mcv`)은 새 llama.cpp 빌드가 있어야 읽힌다. 서버는 b11539 에서 b11701 로 올렸다. `bolt` 는 b11539 에서 로드조차 되지 않았고, `mcv` 도 b11701 이상이 필요하다(PR #29416 이 b11539 보다 나중에 병합됐다)([troubleshooting.md](troubleshooting.md#새-모델이-로드되지-않는다-llamacpp-빌드가-모델보다-오래됨)).
- 한 번에 한 모델만 올린다. 다른 모델을 요청하면 router 가 교체하며 대체로 17~30초(큰 모델은 80초 안팎) 걸린다.
- 통합 메모리가 아닌 일반 외장 GPU 는 시험하지 않았다.

## 7. 클라이언트 사양

- Windows 10/11 x64, PowerShell 5.1 이상(Windows 에 기본 포함).
- 서버와 같은 LAN, 서버의 TCP 8080 에 도달 가능(방화벽에서 이 PC 의 IP 허용).
- opencode v1.18.35 - 설치 스크립트가 설치한다(약 0.2GB, 관리자 권한 불필요).
- 모델은 서버에서 돌아가므로 클라이언트 PC 에 GPU 는 필요 없다.

## 8. 비슷한 서버를 만들 때

1. 통합 메모리(또는 GPU 가 큰 영역을 주소 지정할 수 있는 장비)와 충분한 GTT/VRAM 을 확보한다 - 2절.
2. OS 설정 4가지를 한다 - 4절.
3. llama.cpp 사전빌드(Vulkan)를 ext4 에 풀고 `server/` 의 파일로 router 를 띄운다 - [server.md](server.md#1-처음-세우는-순서).
4. 켠 뒤 **GTT 가 올라갔는지** 확인한다. 확인을 건너뛰어 CPU 로 돌고 있다는 것을 늦게 알아챈 적이 있다.
